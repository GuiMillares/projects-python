1. O QUE É
----------
App de finanças pessoais de dono único. Front-end React (Vite) que no futuro
roda como desktop nativo via Tauri, falando com uma API Python (Flask) local
sobre o MySQL do Laragon.

Repositório: git@github.com:GuiMillares/projects-python.git (branch main)
O projeto fica na subpasta "projeto finanças/" do repositório.


2. ESTRUTURA
------------
projeto finanças/
  db/schema.sql        cria o banco local_finance do zero (idempotente)
  db/migrar.sql        alterações em banco que já existe (idempotente)

3. COMO SUBIR
-------------
a) MySQL do Laragon (pelo painel do Laragon, ou):
   C:/laragon/bin/mysql/mysql-8.4.3-winx64/bin/mysqld.exe \
     --defaults-file=C:/laragon/bin/mysql/mysql-8.4.3-winx64/my.ini

b) Banco, RODANDO DA RAIZ "projeto finanças/":
   mysql -u root --skip-password < db/schema.sql
   mysql -u root --skip-password < db/migrar.sql

c) API (ATENÇÃO: ative o venv certo, ver seção 7):
   cd api
   source ../../.venv/Scripts/activate
   pip install -r requirements.txt      # só na primeira vez
   python criar_usuario.py              # só na primeira vez
   python app.py                        # http://127.0.0.1:8756

d) Telas:
   cd ui
   npm install
   npm run dev                          # http://localhost:1420

No primeiro acesso a tela pede o cadastro do 2FA e mostra o QR code.


4. DECISÕES DE ARQUITETURA (não desfazer sem motivo)
-----------------------------------------------------
* NÃO usa Firebase. O projeto começou com Firebase Auth + Cloud Functions
  (copiado do painel /superadmin do Synchro) e foi migrado para processo
  local a pedido. O mapeamento foi:
      Firebase Auth        -> senha com hashlib.scrypt em seguranca.py
      Cloud Functions 2FA  -> rotas /api/auth/2fa/*
      Documento Firestore  -> tabela usuarios

* INVARIANTE DE SEGURANÇA: o segredo TOTP nunca existe no frontend. É
  gerado no servidor, mora só em usuarios.totp_secret e nenhuma rota o
  devolve. O cliente vê uma única vez o otpauth:// do cadastro (para virar
  QR code) e depois só manda 6 dígitos e recebe sim ou não.
  Se aparecer otplib ou speakeasy no ui/package.json, a regra foi quebrada.

* Login devolve sessão PARCIAL: ela só abre as rotas de 2FA. Nenhum dado
  financeiro sai antes do código ser validado.

* Código TOTP vale UMA vez (janela queimada em usuarios.totp_ultimo_step),
  não os 30 segundos inteiros.

* Dinheiro é DECIMAL no MySQL, nunca FLOAT.

* Toda query passa por parâmetro (%s), nunca por f-string.

* A API escuta só em 127.0.0.1 e aceita uma lista fechada de origens CORS.

* app.py checa a porta antes de subir e recusa se já houver algo lá. Isso
  existe porque o Windows deixa DOIS processos escutarem a mesma porta
  (SO_REUSEADDR), e as respostas passam a se revezar entre eles; quando um
  é de antes de uma alteração, a API parece rodar código velho de forma
  intermitente. Isso já causou confusão duas vezes.

8. COTAÇÃO DA B3 (brapi.dev)
-----------------------------
Investimentos guarda ticker, quantidade e preço médio. O valor atual NÃO é
gravado: é quantidade x cotação do momento.

A brapi descontinuou a v1 (/api/quote/{tickers}?token=) e migrou para v2:
  GET {BRAPI_BASE}/v2/stocks/quote?symbols=TICKER1,TICKER2
com o token (quando existe) no header "Authorization: Bearer SEU_TOKEN",
não mais em ?token= (isso agora só vale pra ferramentas no-code, segundo
a doc deles). O payload de cada item também mudou: os números ficam
aninhados em "data" (res["data"]["regularMarketPrice"]), antes era plano
no próprio item. cotacoes.py já foi corrigido pra isso em 17/08/2026; se
voltar a dar 401 mesmo com token certo, a API pode ter mudado nome do
campo de novo, vale conferir a doc em brapi.dev/docs.

TOKEN: sem token a brapi só responde SEM autenticação pra um punhado de
tickers conhecidos (PETR4, VALE3, MGLU3, ITUB4...) e recusa o resto com
401 MISSING_TOKEN. O código cobre os dois casos:
  sem token -> um request por ticker, no máximo 6 (FIN_BRAPI_MAX_SEM_TOKEN)
  com token -> um request só com a carteira inteira

completos, cotacao null.

FORMULÁRIO DE NOVO INVESTIMENTO: ao digitar um ticker que já parece
completo (4 letras + 1 ou 2 dígitos, ex: PETR4, HGLG11), a tela busca a
cotação sozinha (debounce de 500ms, rota GET /api/cotacoes/<ticker>) e
preenche "Preço médio" com o valor atual, só pra facilitar. Editar esse
campo na mão tem prioridade e para o preenchimento automático: é o preço
que a pessoa realmente pagou que importa, não o preço de agora.

9b. METAS E IA
---------------
XP e nível NÃO são gravados: derivam do que está concluído
(api/gamificacao.py). Bônus da meta = 1.5x a soma das subtarefas, mínimo
50, sempre maior que a soma. Curva: nível 2 aos 100 XP, 3 aos 300, 4 aos
600.

A quebra da meta em passos vive em api/ia.py, o ÚNICO arquivo que fala com
um LLM. Provedor: GOOGLE GEMINI (SDK google-genai), escolhido em 18/08/2026
por causa do tier gratuito sem cartão. Saída estruturada por JSON schema,
thinking em nível MEDIUM (FIN_IA_THINKING), modelo padrão gemini-3.5-flash
(trocável por
FIN_IA_MODELO: gemini-3.5-flash-lite é mais barato, gemini-3.7-flash é
melhor).

O contrato do módulo é (subtarefas, aviso) e ele NUNCA levanta exceção. Foi
o que deixou a troca de provedor (Anthropic -> Gemini) custar um arquivo
só: rotas, banco, gamificação e tela não souberam da mudança.

REFINOS DE 18/08 (tarde), todos testados inclusive com chamada REAL ao
Gemini (a chave foi configurada neste PC):
* Geração mais inteligente: prompt exige passos específicos da meta (com
  contas reais de aporte/prazo), thinking MEDIUM (FIN_IA_THINKING), e a
  rota de "sugerir mais" manda os passos existentes para o modelo

* Escada de níveis: 300 aparências únicas em ui/src/services/niveis.js
  (15 patamares x 4 divisões IV-I x 5 pips, pesquisado em LoL/Duolingo/
  insígnias militares). gamificacao.py trava o nível em NIVEL_MAXIMO=300.
* A DIVISÃO MUDA A BORDA do selo, não só o texto (.fin-selo em app.css,
  seletor data-divisao). IV é anel fino, III é anel cheio, II ganha um
  segundo anel separado por um vão, e I tem o anel externo partido em
  quatro arcos. São três camadas independentes: patamar (ícone e cor) a
  cada 20 níveis, divisão (borda) a cada 5, pips a cada 1.
  Duas decisões desse desenho que NÃO devem ser desfeitas sem medir:
    - o I não se separa do II por brilho, e sim por FORMA. No tema claro o
      brilho some sobre o fundo bege e os dois ficavam idênticos.
    - a falha de baixo-direita do serrilhado cai exatamente onde fica o
      número do nível (.fin-heroi__nivel). Girar o "from 45deg" faz os
      dois brigarem.
  Coroa de louros foi prototipada e DESCARTADA por medida: abaixo de uns
  90px as folhas viram serrilha ilegível e o selo aqui tem 44 a 62px.
* Exclusões confirmam num modal (components/ConfirmarExclusao.jsx), usado
  em Metas (meta e passo), Entradas/Saídas e Investimentos. Foco inicial
  no Cancelar; Esc e clique no véu fecham.
* Metas concluídas vão para a aba "Concluídas" (filtro fin-seg com
  contadores); concluir uma meta a move na hora.

* SESSÃO DE DOIS ESTÁGIOS. Hoje é a tabela `sessoes` com a coluna
  dois_fatores_ok, e o token trafega como hash SHA-256. Vira Firebase Auth
  mais um custom claim marcando que o 2FA passou. Isso mexe no ExigeSessao
  do ui/src/App.jsx E no decorador @exige_sessao das 28 rotas.
  ATENÇÃO: o TOTP NÃO deve ser reimplementado a partir de seguranca.py. Vai
  para Cloud Function, seguindo o padrão do LoginAdmin.jsx da Synchro.
  (Cuidado: o ConfiguracoesAdmin.jsx da Synchro NÃO segue esse padrão, ele
  gera e valida o segredo no browser. É uma inconsistência da Synchro, já
  apontada ao dono. Copiar o Login, nunca o Configurações.)

* FOTO DE PERFIL. Hoje é data URL em MEDIUMTEXT, limitada a 400 KB
  (FOTO_MAX_BYTES em app.py). Documento do Firestore tem teto de 1 MiB,
  então até cabe, mas é desperdício gravar imagem dentro do documento que a
  tela lê a cada carga. O certo é Firebase Storage, que é uma peça a mais
  nas regras e no fluxo.

* ESPAÇOS COMPARTILHADOS. É a mudança mais profunda e não é só um campo
  novo. Hoje TODA rota filtra por usuario_id. Passar a filtrar por espacoId
  faz a posse deixar de ser um número na linha e virar uma consulta de
  associação, tanto no código quanto no firestore.rules. É aqui que mora o
  risco real de vazar dado entre espaços: CONCENTRAR OS TESTES AQUI.
  Modelo combinado: coleção `espacos` com membros (papel dono/membro), e
  transações/metas/orçamentos referenciando espacoId em vez do usuário. A
  UI precisa de um seletor de espaço.

BOA NOTÍCIA: o dashboard já agrega NO CLIENTE. Não existe um GROUP BY ou
SUM em app.py. Essa costuma ser a parte mais dolorosa de migrar pra
